## 上下文 (Context)

TravelMind 需要以下类型的数据：

| 数据类型 | 用途 | 理想来源 |
|---------|------|---------|
| 景点/餐厅/酒店 POI | 行程规划 | 高德/百度地图、携程、美团 |
| 实时天气 | 行程建议 | 天气 API |
| 旅游攻略 | RAG 知识库 | 马蜂窝、小红书、抖音 |
| 长租房源 | 租房推荐 | 贝壳、自如、58 同城 |
| 实时资讯 | 信息增强 | 搜索引擎 |

**核心挑战**：经过深入调研，发现中国主流平台的数据获取**极度受限**：

### 旅游酒店平台
- **携程开放平台**：需企业资质，审核数周，涉及佣金分成
- **美团酒店直连**：需联系商务，无公开文档
- **飞猪开放平台**：基于阿里 TOP，需商家资质
- **马蜂窝**：无攻略内容 API，仅商品管理接口

### 长租房平台
- **贝壳开放平台**：仅面向金融机构、政务等 B 端，需商业合作协议
- **自如/万科泊寓/龙湖冠寓**：无公开 API
- **58 同城**：需企业审核
- **蛋壳公寓**：2021 年已退市停运

### UGC 平台
- **抖音开放平台**：仅支持用户授权获取自己的内容，无公开搜索 API
- **小红书**：无内容 API，2024 年起诉蝉小红判赔 490 万元

### 法律风险
- 厦门房麦公司因爬取房产网站数据，被判**非法获取计算机信息系统数据罪**
- 最高检明确：爬取数据须遵规，绕过反爬措施可能构成犯罪

## 考虑的备选方案 (Alternatives Considered)

### 方案 A: 仅使用官方开放 API

**可用资源**：
| 平台 | 个人可用 | 数据类型 | 免费额度 |
|------|---------|---------|---------|
| 高德地图 | ✅ | POI、导航、天气 | 900 万次/月 |
| 百度地图 | ✅ | POI、地理编码 | 10 万次/日 |
| 和风天气 | ✅ | 天气预报 | 1000 次/日 |
| 博查搜索 | ✅ | 网页搜索 | 有限免费 |

**优势**：
- 完全合法合规
- 稳定可靠
- 免费额度足够个人项目

**劣势**：
- 无法获取 OTA 酒店价格、长租房源、UGC 攻略内容
- 功能完整度受限

### 方案 B: 爬虫采集

**优势**：
- 可获取任意公开数据

**劣势**：
- **法律风险极高**：已有刑事判例
- 违反平台 Robots 协议和用户协议
- 反爬对抗成本高
- 数据质量和时效性难保证
- 个人项目不值得冒险

**结论**：❌ 明确排除

### 方案 C: 第三方数据服务商

**可选服务**：
- 中指数据：专业房产数据，企业付费
- 蝉妈妈/飞瓜：已因法律问题受限
- 数据堂等：需商业合作

**劣势**：
- 成本高，个人项目难以承受
- 数据来源合规性存疑
- 可能存在连带风险

### 方案 D: 混合策略 - 官方 API + AI 生成 + 示例数据

**思路**：
1. **真实数据**：使用高德地图 POI、天气等完全开放的 API
2. **AI 生成**：旅游攻略由 LLM 根据 POI 信息生成
3. **示例数据**：长租房使用结构化的模拟数据集，展示系统能力
4. **可扩展设计**：预留接口，未来有官方渠道时可快速接入

## 决策 (Decision)

**采用方案 D：混合策略**

### 数据源配置

```yaml
# config/data_sources.yaml
data_sources:
  # 真实 API - 生产使用
  poi:
    provider: "amap"  # 高德地图
    api_key: "${AMAP_API_KEY}"
    endpoints:
      - place/text  # POI 搜索
      - place/around  # 周边搜索
      - direction/v2/driving  # 路径规划
    rate_limit: 900_0000  # 月配额
  
  weather:
    provider: "qweather"  # 和风天气
    api_key: "${QWEATHER_API_KEY}"
    endpoints:
      - weather/7d  # 7 天预报
      - indices/1d  # 生活指数
  
  search:
    provider: "bochaai"  # 博查搜索
    api_key: "${BOCHA_API_KEY}"
    use_case: "实时资讯检索"

  # AI 生成 - 弥补内容空白
  travel_guide:
    provider: "llm_generated"
    strategy: "基于 POI 数据生成攻略文案"
    cache: true  # 缓存生成结果
  
  # 模拟数据 - 展示系统能力
  rental:
    provider: "mock"
    data_file: "data/mock_rentals.json"
    note: "展示数据结构和系统能力，非真实房源"
```

### 关键设计原则

1. **透明声明**：在 README 和 UI 中明确说明数据来源和限制
2. **接口抽象**：`DataProvider` 抽象层，未来可无缝切换真实数据源
3. **能力展示优先**：重点展示架构设计和 Agent 编排能力，而非数据完整性

## 后果 (Consequences)

### 正面影响

- ✅ 完全合法合规，零法律风险
- ✅ 核心功能（POI 搜索、天气、路径规划）使用真实数据
- ✅ 架构设计支持未来扩展
- ✅ 面试时可坦诚解释技术决策的权衡过程

### 负面影响

- ⚠️ 长租房功能无真实数据，功能演示性质
- ⚠️ 旅游攻略为 AI 生成，可能不如 UGC 内容丰富

### 面试话术

> "在调研阶段，我发现国内 OTA、长租房平台、UGC 平台的 API 都不对个人开发者开放。我评估了爬虫采集的方案，但考虑到已有刑事判例（厦门房麦案、小红书诉蝉小红案），法律风险过高。
>
> 最终我采用了混合策略：核心的 POI 和天气数据使用高德地图等官方 API；旅游攻略由 LLM 基于真实 POI 信息生成；长租房使用结构化的模拟数据展示系统能力。
>
> 架构上我设计了 `DataProvider` 抽象层，如果未来有官方合作渠道或企业资质，可以快速切换到真实数据源，而不需要修改上层业务逻辑。
>
> 我认为这个决策体现了**工程师的职业判断**——在合规约束下最大化技术价值。"
